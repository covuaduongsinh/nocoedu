# NocoEdu (training management)

Business code of the club's training system. Read this before changing students, classes, attendance or tuition.

- **Data owner.** NocoEdu owns student and parent data. Other apps read it only through `GET /api/ext/*` with an API key of a service account that holds nothing but `edu_api_doc` (`server/routes/edu-ext.ts`). Never add a write there; never return more than a student code, a short name, the level, the class and a parent code.
- **Child data.** A birth year, and the full date of birth only in `eduHocVien.ngaySinh` (kept at the head coach's request, DS-60; read only through `POST /hocVien/ngaySinh`); no photo, school or address. Seeds, tests and logs use made-up names ("Học viên Mẫu 01"). A CSV import prints counts and reasons, never names or phone numbers.
- **Where things are.** Collections `edu*` in `database/main/migrations/202611090001_create_edu_tables.ts` (dates are `YYYY-MM-DD` text, times `HH:mm`, months `YYYY-MM`; booleans are written `true`/`false` so SQLite and Postgres behave the same). Business actions and the fields they read or write: `server/edu/permissions.ts`. Data scopes: `server/edu/record-access.ts`. Routes: `server/routes/edu-*.ts`. Pages: `client/pages/edu/`. Copy in three languages: `client/locales/edu-copy.ts` (Vietnamese is the default).
- **Permission sets** are seeded once and never assigned to anybody. They live twice: `database/seed-data/edu-permission-sets.ts` (source) and the literal in `database/main/seeds/202611090002_edu_permission_sets.ts`, because a seed cannot import application code. After changing the source run `pnpm exec tsx scripts/generate-edu-permission-seed.mts`; `tests/server/edu-permission-sets.test.ts` fails when they differ. Once the seed has run on a database, change it with a new seed, not by editing this one.
- **Routes.** Every route has `auth.required()` and an explicit composite-action check; guards are installed on the route's own paths, never `router.use('*')` (an unrelated path would answer 401 instead of 404; `tests/server/app-server.test.ts` catches it). Standard Repository writes (`createOne`, `updateOne`, `deleteOne`) need an `Idempotency-Key` header; the business routes under `/api/hocVien/...`, `/api/phuHuynh/...`, `/api/dongY/...` do not.
- **Record scopes** that depend on a row of the request itself (a student's `coSoId`, a class's `hlvId`) must filter on that column, not on ids fetched earlier in the request, or a row created in the same request is out of scope.
- **Ids** are auto-increment integers; `ma` (HS00001, PH00001) is the stable code shared with other apps.
- **Tests** run one file at a time: `pnpm exec vitest run tests/server/edu-scope.test.ts`. They share one application per file, so each case resets the school with `seedSchool` in `tests/helpers/edu.ts`.

- **Writes name a parent.** The generated `createOne` scopes reads and edits, not the parent a new row points at. `edu-data.ts` checks the branch of a new class and the class of a new timetable row; a student's class changes only through `/hocVien/chuyenLop`; parent links are created only by `/phuHuynh/taoMoi`, which reuses a phone number only for a parent the caller already sees. Add the same check for every new collection with a parent id.

- **Balance.** `eduHocVien.soBuoiConLai` is never written by a client. It moves only in `server/routes/edu-hoc-phi.ts` (`moveBalance`), in the same transaction as the ledger row, guarded by the balance it was computed from. Deduction rules are in `server/edu/so-du.ts` (tested without a database); the make-up rule is recorded in `.nb-studio/memory/hoc-bu-tru-buoi.md`. Composite actions used with `authorizeRepository` must have one collection and one scope, so tuition is split in `edu.goiHoc`, `edu.thanhToan` and `edu.soDu`. Bank details for VietQR come from `EDU_VIETQR_*` environment variables only.
- **Scope filters** use `anyOf` (`server/edu/filters.ts`), which groups the OR conditions at most 64 per group; a flat OR of more than about 1000 ids fails on SQLite.
- **Test ids** are never inserted by hand (`seedSchool` returns them): a hand-written id does not advance a PostgreSQL sequence.
- **Reports and exports** (`server/routes/edu-bao-cao.ts`) read through the policy of the composite action that guards the data (revenue → `edu.thanhToan`, attendance → `edu.diemDanh`, the rest → `edu.hocVien`); never read a table raw for a role's report except to aggregate rows whose ids a policy already returned. Every export (CSV or comment text) writes one `eduXuatDuLieuNhatKy` row: who, which report, how many rows, never names. CSV cells go through `csvCell` (formula guard).
- **CSV import** is `server/edu/import-csv.ts` behind `cli/commands/edu/import-hoc-vien.ts`: all or nothing, reports line numbers and reason codes only.
- **CSV export of students** (DS-60 PR 6): `server/routes/edu-xuat-csv.ts` (`POST /hocVien/xuatCsv`), page `client/pages/edu/xuat-csv.tsx`; needs `edu.hocVien` `export` (Quản trị, Quản lý cơ sở; seed `202611110002_edu_hoc_vien_export_grant`, left out of `…0002` by the generator like `import`). Columns are those of the import file (`IMPORT_COLUMNS`), nothing else (no full date of birth, note or balance); read only through the policies of the action, a branch or class outside the scope in the filter is 403; at most `MAX_EXPORT_STUDENTS` (5,000) students; cells go through `csvCell`; one `eduXuatDuLieuNhatKy` row per export (`loai = hoc_vien_csv`), file not stored.
- **CSV import on the students page** (DS-60 PR 5): `server/routes/edu-nhap-csv.ts` (`/hocVien/nhapCsv/xemTruoc`, `/xacNhan`, `/mau`) → `server/edu/import-web.ts` (`planImport` writes nothing, `applyImport` writes in one transaction) reusing `readRow` of `import-csv.ts`; page `client/pages/edu/nhap-csv.tsx`. It needs `edu.hocVien` `import` (Quản trị, Quản lý cơ sở; added by the seed `202611110001_edu_hoc_vien_import_grant`, because `…0002` had already run, so `scripts/generate-edu-permission-seed.mts` leaves that action out of `…0002`). The `branches` and `classes` scopes of the action decide where a caller may import: only branches and classes in that scope are looked up, so another branch's code is reported as `UNKNOWN_*` exactly like a code that does not exist (no probing). Unlike the command-line import, a repeat is not an error. Each row is matched on its own phone: an existing student is the same child only when name + birth year + branch agree **and** a parent with the row's phone is linked (as in the Lark import); a parent is reused by phone among those the caller sees. Rows of one key in the file merge only when they all point at one existing student or none matches an existing one (then one new child with several parents); otherwise all of them are `AMBIGUOUS_STUDENT`. Warnings (`STUDENT_LEFT`, `POSSIBLE_DUPLICATE`) never block. A confirmation runs in the `edu:nhap-csv` mutex because `eduHocVien` has no unique key. The file travels in the JSON body (`csv`, at most 512 K characters and 2,000 rows), is never stored; each confirmation writes one `eduNhapLarkNhatKy` row (`tongKet.nguon = 'csv_hoc_vien'`, counts only; a refused confirmation is `tu_choi`). **Sample data** (`server/edu/sample-data.ts`, registered in `server/providers/edu-sample-data.ts`) loads only under `APP_SAMPLE_DATA`; names say "Mẫu", no real data, no password in the repository.

Keys of earlier runs (`lark:ph:*`, `lark:sodu:*`) are recognised, never duplicated (`docs/lark/nhap-production.md`). **The money** is in `Tổng Deal (HP + book)` (DS-61): `thanh-toan.ts` turns its tuition into `eduThanhToan` rows (`externalId = lark:tongdeal:<rec>`, `hinhThuc = khong_ro`, branch of the student), written in the same transaction after the packages and so simulated by the dry run too; a row without a student, a date or a package is reported with its amount, never guessed. Rules to confirm: `TONG_DEAL_RULES`. **Books** (`sach.ts`, DS-61 E): the table `Sách` becomes the catalogue `eduSach` (`lark:sach:<rec>`, optional table, written in the same transaction, never edited afterwards, a symbol typed by hand is kept). The catalogue is global (`allRecords`): only the administrator manages it; the grants were added to the seeded sets by `202611130003_edu_sach_grant`, which is why `scripts/generate-edu-permission-seed.mts` leaves `edu.sach` out of `…0002` (on Windows turn the seed's CRLF into LF before running the generator). **Books handed out** (`eduPhatSach`, DS-61 E2): one row per book given to a student; the page `edu.phatSach` and the composite `edu.phatSach` (view, manage) are held by the administrator (all), the branch manager (`edu.myBranches`, by the student of the row) and the accountant (view); a coach has neither (the row carries a price). The book fund (`/quySach/xem`, view of `edu.phatSach`, summed only over the students the caller sees) is `eduNopSach` (book money paid, migration `…0003`; imported from `Tổng Deal`.`Tiền sách`, `lark:tongdeal-sach:<rec>`) minus `eduPhatSach.tienSach`; `POST /nopSach/ghi` records book money paid (needs `edu.phatSach.manage` and a student the caller sees; the branch comes from the student), besides the Lark import. **Admissions** (`eduLienHe`, DS-61 D): a family that has not enrolled, by design only the parent's name and phone, branch, channel, status (`moi`, `dang_cham_soc`, `da_chot`, `khong_chot`), a call-back day, a short note and the day it was made; no address, no social profile, no data of a child, and nothing is imported from Lark. Only the administrator and the branch manager (`edu.myBranches` by `coSoId`) hold `edu.tuyenSinh`; accountant and coach hold nothing. Retention rule the club agreed to by default: a contact is deleted (the page has a delete button) when it is no longer needed, at the latest a year after `ngayTao`; nothing deletes it by itself: `POST /lienHe/donQuaHan` (button on the page, `edu.tuyenSinh.manage`, over the caller's scope) deletes every contact made over 365 days ago. Grants: `202611140004_edu_tuyen_sinh_grant`. **Coach profiles and pay** (`eduHoSoGv`, DS-61 F): one profile per coach account (`userId`, never changed afterwards), short name, position, status and the pay for one session; no identity papers, bank account or social profile. Only the administrator holds `edu.hoSoGv` (page and view/manage): pay is private. `POST /hoSoGv/thuLao {thang}` sums, per profile, the sessions of that month with `trangThai = da_diem_danh` taught by the account times its pay. Grant: `202611140005_edu_ho_so_gv_grant`. **Books of a student** (`eduSachHoc`, DS-61 E4): `dang_hoc` or `da_hoc` per student and book (one row each; finished wins), written only by `import-lark` from `HocVien`.`Sách đang học` / `Sách đã học` (`lark:sachhoc:<student rec>:<book rec>`), shown on the "Sách" tab of the student's file. ## Which sessions were deducted from which package (DS-60 PR 3)

`POST /goiHoc/chiTiet` (`server/routes/edu-hoc-phi.ts`) answers `{ goiHocId }` with the package, `daDung`, `conLai`, the
sessions deducted from it (`cacBuoi`) and `vuotSoDu` (sessions beyond everything the student bought). It needs
`edu.goiHoc` `view` for the package (so a coach gets 403 and a branch manager sees their branch only) and `edu.soDu`
`view` for the ledger. Nothing is stored: `server/edu/phan-bo-goi.ts` works the allocation out on every read, first in
first out, from the packages (by `ngayMua`, then id) and the ledger (the sum per attendance row, so a refund cancels its
deduction; a positive `dieu_chinh` without a package counts as a package of its own, a negative one as a deduction
without a session). A deduction takes the earliest package with room, whatever the date of the session; the rules are
at the top of that file and are the only place to change them. `useRows(name, { newestFirst: true })` reads a growing
collection (sessions) newest first, so its cap of 2,000 rows never drops the newest.

## Editing and removing (DS-60 PR 4)

Edit buttons and dialogs live in `client/pages/edu/sua-xoa.tsx` (`RowManage` for branch, class, student and parent;
`NoteButton` for a coach's note; `UnlinkButton` for a student–parent link). They use the standard `updateOne` and
follow the person's `manage` grant, but the server decides: `server/routes/edu-data.ts` checks the grant, the record
scope and the allowed fields, and `server/edu/sua-ban-ghi.ts` (`checkUpdate`, pure, no database) checks the values (a
status from the list, a phone number already normalised, a class level key that agrees with its order). A class or a
timetable row cannot be moved to a parent outside the caller's scope. **Nothing is deleted except a parent that no
student link and no consent refer to** (`POST /phuHuynh/xoa`): a branch is set to `tam_dung`, a class to `da_dong`, a
student to `da_nghi`, so attendance, packages and the balance ledger stay. Never add a hard delete for those three. A
student's class changes only through `/hocVien/chuyenLop`; the balance and the level never through `updateOne`. Removing
a package is not offered; when it is, it must write a ledger row that returns its sessions (see `phan-bo-goi.ts`).

## Hardening of the routes added late (GĐ 0 of `docs/plans/2026-11-17-tai-cau-truc-nocoedu.md`)

Routes written after the first release did not follow the rules above; GĐ 0 brought them back. What each one needs now:

- **One place moves a balance.** `server/edu/balance.ts` holds `moveBalance` (balance + ledger row, guarded by the balance it was computed from), `balanceOf`, `lockSessionRule` (fixes `truVangCoPhep`/`truVangKhongPhep` on the session at its first save) and `saveAttendanceRow` (one attendance row: an unchanged status keeps what was deducted, a row with `tinhVaoSoDu = false` never moves the balance, only the difference is written). The register (`/diemDanh/luu`), the quick edit of the reconciliation page (`/doiSoat/capNhatBuoiHoc`) and the CSV import all call them; never write `soBuoiConLai` anywhere else, and never recompute it from "packages − registers" (that overwrites an opening balance).
- **Backup and restore** (`/heThong/backup/exportJson`, `/importJson` in `server/routes/edu-crm-backup.ts`) need `edu.heThong` `backup` / `restore`, held by the administrator set only (page `edu.heThong` too, route `/sao-luu`; seed `202611170001_edu_he_thong_grant`, left out of `…0002` by the generator). They are the one place that reads and writes the tables directly, because a snapshot is not a report of what one branch may see. `BACKUP_TABLES` lists the 30 tables of the club's own data in the order a restore writes them (parents first); **a table added by a later phase is added there in the same change, and the round-trip test (`tests/server/edu-crm-backup.test.ts`, `everyTable`) gets a row for it**. A restore checks every row before writing (only known tables and columns, a whole-number `id`, no `id` twice, a known `phienBan`), never overwrites a row whose `id` exists, writes everything in one transaction (or nothing), has a dry run (`chiKiemTra`: counts only; the page shows it before the confirmation), and on PostgreSQL moves the `id` sequences of what it wrote (`dayTuTangDaDat`; if it is `false`, run `select setval(pg_get_serial_sequence('"<schema>"."<table>"', 'id'), max(id)) from "<schema>"."<table>"` for each restored table before more data is entered). `eduCoSoQuanLy.userId` and `eduHoSoGv.userId` name accounts a snapshot does not hold: restoring into a database without those accounts brings the rows back and they work once the accounts exist. A snapshot restores into the same kind of database it came from (a SQLite file into SQLite, a PostgreSQL one into PostgreSQL). Every use writes one `eduXuatDuLieuNhatKy` row (`sao_luu_json`, `khoi_phuc_json`). A snapshot holds children's data (birth dates, parents' phones): the page says so.
- **CRM webhook** (`/edu/crm/lead-sync`): no session, so it is guarded by the secret in `EDU_CRM_WEBHOOK_TOKEN`, sent in the `x-crm-token` header (never in the address). No variable = every call is refused (403 `CRM_SYNC_NOT_CONFIGURED`); a wrong or missing header is 401. No default secret exists anywhere, and the admissions page never shows one. Set the variable in the deployment, not in the repository.
- **CSV exports of attendance and tuition** (`/diemDanh/xuatCsv`, `/hocPhi/xuatCsv`) need `edu.baoCao` `export` (a coach cannot take the file) and read through the `view` policies of the data they list (`edu.diemDanh`, `edu.buoiHoc`, `edu.goiHoc`, `edu.hocVien`, `edu.lop`, `edu.coSo`); a class or branch outside the scope is 403, a row of a student the caller does not see is left out, more than `MAX_CSV_ROWS` (100,000) is refused. The students and the sessions/classes are read through their policies; the register and the packages are then read by those ids (a policy page per hundred rows cost a scope lookup each, 75 s for a branch manager's tuition file; now ~0.1 s). The attendance export defaults to the current month when no class is named. Each export writes one `eduXuatDuLieuNhatKy` row (`diem_danh_csv`, `hoc_phi_csv`). The pages show their "Xuất CSV" button only to a person who holds that action.
- **Universal CSV import** (`/edu/import/mau|xem-truoc|xac-nhan/:entity`, `server/routes/edu-import-universal.ts`): `ENTITY_GATES` names the action that owns each entity (`manage` of its resource, `record` for attendance) and it is checked before the body is read; every lookup (branch, class, student, book) and every write goes through the policies of that action and of the `view` actions it points at, so a code outside the scope is "not found". A package adds its sessions through `moveBalance` (reason `mua_goi`), attendance deducts through `saveAttendanceRow` with the rule fixed on the session, and a session the import has to create is `da_diem_danh`. One transaction per row; the answer lists refused rows as line + reason code only, never a name or a phone number; at most `MAX_IMPORT_ROWS` (5,000) rows a file. The profile of a coach resolves the account in the `user` table (an id or an e-mail), never `users`.
- **Reconciliation page** (`/doiSoat/*`): `tongQuan` reads everything through the policies of the money actions (`edu.goiHoc`, `edu.thanhToan`, `edu.phatSach`, `edu.diemDanh`, `edu.buoiHoc`; a role without them, a coach, gets 403) and show parents/classes/branches only when the caller also holds `edu.phuHuynh`, `edu.lienKet`, `edu.lop`, `edu.coSo`. The students are read through their policy and every other figure is taken over exactly those students' ids (`rowsForStudents`: packages, payments, books handed out, book money paid, sessions deducted, parents; the caller must hold the action that owns each, checked first) — reading each table page by page through its own policy cost ~40 s for a branch manager with 2,000 students, now ~0.15 s. The awareness score is not a permission field. **"Sessions studied" is the sum of `soBuoiDaTru`** on the audit page and in the student file, never the number of attendance rows. **`eduPhatSach.tienSach` is already net of the discount** (`giaBan - uuDai`): never subtract `uuDai` again.
- **Monthly comments** `lichSuBuoiHoc` and `aiGoiY` check the student through `edu.hocVien` `view` (outside the scope is "not found") and read attendance and sessions through `edu.diemDanh` / `edu.buoiHoc`.
- **Shared reading helpers**: `server/edu/read-all.ts` (`readAllRows` pages a policy-checked read and refuses more than a cap, `chunksOf`). Tests for all of the above: `tests/server/edu-crm-backup.test.ts`, `edu-import-universal.test.ts`, `edu-doi-soat.test.ts`, `edu-ho-so.test.ts`; client: `tests/client/edu-hoc-phi.test.tsx`, `edu-diem-danh.test.tsx`, `edu-tuyen-sinh.test.tsx`, `edu-home.test.tsx`, `client-routes.test.ts`.
- **PostgreSQL.** Production runs PostgreSQL; the tests run SQLite unless told otherwise. Run a file on PostgreSQL with `NOCOBASE_TEST_DB_DIALECT=postgres POSTGRES_HOST=… POSTGRES_PORT=5432 POSTGRES_USER=… POSTGRES_PASSWORD=… POSTGRES_DATABASE=postgres pnpm exec vitest run tests/server/<file>` (`docs/ci-postgres-job.md`). - Report `loHongKienThuc` in `/baoCao/xem` and `/baoCao/xuatCsv` (gate `edu.kienThuc` `view`; needs `edu.diemDanh`, `edu.buoiHoc` and `edu.chuongTrinh` `view` too; more than `MAX_ROWS` rows is refused).

**The rules.** _Learned:_ when a register is saved (`/diemDanh/luu`), or a status is corrected (`/doiSoat/capNhatBuoiHoc`, the universal import), or the skills of a session are chosen, `refreshTaughtKnowledge` (`kien-thuc-doc.ts`) writes `da_hoc` for the students present (`co_mat`, `hoc_bu`) on the skills taught to the class or to the group they are in now. It only inserts when the student has no row for the skill, so a grade by hand or another session's row is never overwritten; rows it wrote itself (`nguon = buoi_hoc`, `mucDo = da_hoc`, pointing at the session) are taken back first, then every session that teaches the same skills is walked again, so a student corrected to absent loses the row and a skill taught twice still counts. This is the one write of the system that does not go through a policy: it runs in the transaction of the register, after the students were checked against the caller's scope, like the ledger rows of the balance. _Gap_ (`deriveGaps`): a skill taught in a session of the student's **own current class** (to the whole class or to the student's group) while the student has an **absence row** (`vang_co_phep`, `vang_khong_phep`) and no state for the skill; or a skill graded `chua_vung`. A make-up (`hoc_bu` where the skill is taught again) or any later grading closes it. A student with no row at all in a session (joined later) is not a gap. Only active skills of active topics count. _Progress:_ skills with `da_hoc`, `dat` or `vung` over the active skills of the level; `chua_vung` is not learned.

Copy: `client/locales/edu-copy-kien-thuc.ts`. Tests: `tests/server/edu-kien-thuc.test.ts`, `edu-kien-thuc-rules.test.ts`, `tests/client/edu-kien-thuc.test.tsx`, migration in `tests/database/edu-migrations.test.ts`. Do not read a knowledge table through a policy by a long id list again.

Administrator all, branch manager their branches, coach their classes; the accountant has neither the page nor the composite. Several collections, so the composite is used with `needs()` only, never through a record API. `eduBaiKiemTraKyNang` has **no permission of its own**: it is read and written by the id of a test the `bai` policy returned (a test belongs to one class, so the test decides), the same pattern as `rowsForStudents`; the marks of a test are read by `baiKiemTraId` the same way and then narrowed to students the caller's `edu.hocVien` policy returns. **Resolve every policy before `database.transaction` opens**: authorizing reads the database through another connection, and inside a transaction on a one-connection pool (SQLite) that deadlocks (`/kiemTra/nhapDiem` timed out until the student policy was fetched first).

**Routes** (`server/routes/edu-kiem-tra.ts`; pure rules `server/edu/kiem-tra.ts`; tests `tests/server/edu-kiem-tra.test.ts`, `edu-kiem-tra-rules.test.ts`, migration in `tests/database/edu-migrations.test.ts`). `POST /kiemTra/danhSach` (view; filters `lopId`, `coSoId`, `loai`, `trangThai`, `levelKey`, `tim`; `trang`, `limit` ≤ 100, 25 by default, newest first; the multi-collection composite cannot use `usePagedRows`, so the page reads this route with `useRequest`), `/kiemTra/chiTiet {id}` (view: the test, its skills with names, the roster, every mark, a summary per student, `coTheSua`), `/kiemTra/luu` (manage: create, or edit by `id`), `/kiemTra/nhapDiem {id, o: [{hocVienId, kyNangId, diem | null}]}` (manage, ≤ 500 cells, `null` clears), `/kiemTra/chot {id}` (manage) and `/kiemTra/hocVien {hocVienId}` (view: the closed tests of one student, for the student file). One lock, `TEST_LOCK` (`edu:kiem-tra`), is taken by edit, entering marks and closing, so a mark can never land in a test while it closes.

- A test is made for a class the caller sees (`edu.lop` `view`; another branch's class is 404), with active skills of the level of the test (`EDU_SKILL_WRONG_LEVEL`, `EDU_SKILL_HIDDEN`), at least one and at most 50. **It is edited only while it is a draft and has no mark** (`EDU_TEST_CLOSED`, `EDU_TEST_HAS_RESULTS`; clearing every mark makes it editable again). These two are `FAILED_PRECONDITION`, which this application answers with HTTP 400.
- A mark needs a student the caller sees through `edu.hocVien` (else 404) **who is in the class of the test** (`EDU_STUDENT_NOT_IN_CLASS`), a skill of the test (`EDU_SKILL_NOT_IN_TEST`) and a whole number from 0 to the top mark (`EDU_SCORE_OUT_OF_RANGE`); a closed test takes none. Everything is checked before the first write.
- **Pass rule** (`kiem-tra.ts`, integer arithmetic): a student passes when the sum of the marks over the sum of **every** top mark of the test reaches `diemDat`; a skill without a mark counts 0 in the total; a student with no mark at all was not tested. **Closing** (`/kiemTra/chot`, needs at least one mark) writes `eduHocVienKyNang` with `nguon = kiem_tra`, `buoiHocId` null, for every student × skill that has a mark: below `diemDat` is `chua_vung`, from `diemDat` `dat`, from 90% (and not below `diemDat`) `vung`. The test is the latest assessment, so it replaces a hand grade or a `da_hoc` row; a skill with no mark is left alone. A student the closer does not see is skipped and counted (`boQua`). Closing is guarded by the status, so a second close writes nothing.
- **Nobody is moved up by a test.** A closed `len_cap` test lists a student as eligible (`denLevelKey` = the level after the tested one) only when the student passed and is still **at the tested level**; the level is read live, so after `/hocVien/lenCap` the student shows "Đã lên cấp" (`daLenCap`) instead. A `dinh_ky` test never lists anybody. The close answer also carries `lenCap: [{hocVienId, phanTram, denLevelKey}]`.
- Measured (SQLite, a coach with 1,000 students in scope, a class of 40 and 8 skills): entering 320 marks ~0.2 s, closing ~0.2 s, the detail ~0.04 s.
