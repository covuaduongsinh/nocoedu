# NocoEdu (training management)

Business code of the club's training system. Read this before changing students, classes, attendance or tuition.

- **Data owner.** NocoEdu owns student and parent data. Other apps read it only through `GET /api/ext/*` with an API key of a service account that holds nothing but `edu_api_doc` (`server/routes/edu-ext.ts`). Never add a write there; never return more than a student code, a short name, the level, the class and a parent code.
- **Child data.** A birth year, and the full date of birth only in `eduHocVien.ngaySinh` (kept at the head coach's request, DS-60; read only through `POST /hocVien/ngaySinh`); no photo, school or address. Seeds, tests and logs use made-up names ("Học viên Mẫu 01"). A CSV import prints counts and reasons, never names or phone numbers.
- **Where things are.** Collections `edu*` in `database/main/migrations/202611090001_create_edu_tables.ts` (dates are `YYYY-MM-DD` text, times `HH:mm`, months `YYYY-MM`; booleans are written `true`/`false` so SQLite and Postgres behave the same). Business actions and the fields they read or write: `server/edu/permissions.ts`. Data scopes: `server/edu/record-access.ts`. Routes: `server/routes/edu-*.ts`. Pages: `client/pages/edu/`. Copy in three languages: `client/locales/edu-copy.ts` (Vietnamese is the default).
- **Permission sets** are seeded once and never assigned to anybody. They live twice: `database/seed-data/edu-permission-sets.ts` (source) and the literal in `database/main/seeds/202611090002_edu_permission_sets.ts`, because a seed cannot import application code. After changing the source run `pnpm exec tsx scripts/generate-edu-permission-seed.mts`; `tests/server/edu-permission-sets.test.ts` fails when they differ. Once the seed has run on a database, change it with a new seed, not by editing this one.
- **Routes.** Every route has `auth.required()` and an explicit composite-action check; guards are installed on the route's own paths, never `router.use('*')` (an unrelated path would answer 401 instead of 404; `tests/server/app-server.test.ts` catches it). Standard Repository writes (`createOne`, `updateOne`, `deleteOne`) need an `Idempotency-Key` header; the business routes under `/api/hocVien/...`, `/api/phuHuynh/...`, `/api/dongY/...` do not.
- **Record scopes** that depend on a row of the request itself (a student's `coSoId`, a class's `hlvId`) must filter on that column, not on ids fetched earlier in the request, or a row created in the same request is out of scope.
- **Ids** are auto-increment integers; `ma` (HS00001, PH00001) is the stable code shared with other apps.
- **Tests** run one file at a time: `pnpm exec vitest run tests/server/edu-scope.test.ts`. They share one application per file, so each case resets the school with `seedSchool` in `tests/helpers/edu.ts`.

- **Writes name a parent.** The generated `createOne` scopes reads and edits, not the parent a new row points at. `edu-data.ts` checks the branch of a new class and the class of a new timetable row; a student's class changes only through `/hocVien/chuyenLop`; parent links are created only by `/phuHuynh/taoMoi`, which reuses a phone number only for a parent the caller already sees. Add the same check for every new collection with a parent id.

- **Balance.** `eduHocVien.soBuoiConLai` is never written by a client. It moves only in `server/routes/edu-hoc-phi.ts` (`moveBalance`), in the same transaction as the ledger row, guarded by the balance it was computed from. Deduction rules are in `server/edu/so-du.ts` (tested without a database); the make-up rule is recorded in `.nb-studio/memory/hoc-bu-tru-buoi.md`. Composite actions used with `authorizeRepository` must have one collection and one scope, so tuition is split in `edu.goiHoc`, `edu.thanhToan` and `edu.soDu`. Bank details for VietQR come from `EDU_VIETQR_*` environment variables only.
- **Scope filters** use `anyOf` (`server/edu/filters.ts`), which groups the OR conditions at most 64 per group; a flat OR of more than about 1000 ids fails on SQLite.
- **Test ids** are never inserted by hand (`seedSchool` returns them): a hand-written id does not advance a PostgreSQL sequence.
- **Reports and exports** (`server/routes/edu-bao-cao.ts`) read through the policy of the composite action that guards the data (revenue → `edu.thanhToan`, attendance → `edu.diemDanh`, the rest → `edu.hocVien`); never read a table raw for a role's report except to aggregate rows whose ids a policy already returned. Every export (CSV or comment text) writes one `eduXuatDuLieuNhatKy` row: who, which report, how many rows, never names. CSV cells go through `csvCell` (formula guard).
- **CSV import** is `server/edu/import-csv.ts` behind `cli/commands/edu/import-hoc-vien.ts`: all or nothing, reports line numbers and reason codes only.
- **CSV export of students** (DS-60 PR 6): `server/routes/edu-xuat-csv.ts` (`POST /hocVien/xuatCsv`), page `client/pages/edu/xuat-csv.tsx`; needs `edu.hocVien` `export` (Quản trị, Quản lý cơ sở; seed `202611110002_edu_hoc_vien_export_grant`, left out of `…0002` by the generator like `import`). Columns are those of the import file (`IMPORT_COLUMNS`), nothing else (no full date of birth, note or balance); read only through the policies of the action, a branch or class outside the scope in the filter is 403; at most `MAX_EXPORT_STUDENTS` (5,000) students; cells go through `csvCell`; one `eduXuatDuLieuNhatKy` row per export (`loai = hoc_vien_csv`), file not stored.
- **CSV import on the students page** (DS-60 PR 5): `server/routes/edu-nhap-csv.ts` (`/hocVien/nhapCsv/xemTruoc`, `/xacNhan`, `/mau`) → `server/edu/import-web.ts` (`planImport` writes nothing, `applyImport` writes in one transaction) reusing `readRow` of `import-csv.ts`; page `client/pages/edu/nhap-csv.tsx`. It needs `edu.hocVien` `import` (Quản trị, Quản lý cơ sở; added by the seed `202611110001_edu_hoc_vien_import_grant`, because `…0002` had already run, so `scripts/generate-edu-permission-seed.mts` leaves that action out of `…0002`). The `branches` and `classes` scopes of the action decide where a caller may import: only branches and classes in that scope are looked up, so another branch's code is reported as `UNKNOWN_*` exactly like a code that does not exist (no probing). Unlike the command-line import, a repeat is not an error. Each row is matched on its own phone: an existing student is the same child only when name + birth year + branch agree **and** a parent with the row's phone is linked (as in the Lark import); a parent is reused by phone among those the caller sees. Rows of one key in the file merge only when they all point at one existing student or none matches an existing one (then one new child with several parents); otherwise all of them are `AMBIGUOUS_STUDENT`. Warnings (`STUDENT_LEFT`, `POSSIBLE_DUPLICATE`) never block. A confirmation runs in the `edu:nhap-csv` mutex because `eduHocVien` has no unique key. The file travels in the JSON body (`csv`, at most 512 K characters and 2,000 rows), is never stored; each confirmation writes one `eduNhapLarkNhatKy` row (`tongKet.nguon = 'csv_hoc_vien'`, counts only; a refused confirmation is `tu_choi`). **Sample data** (`server/edu/sample-data.ts`, registered in `server/providers/edu-sample-data.ts`) loads only under `APP_SAMPLE_DATA`; names say "Mẫu", no real data, no password in the repository.
- **Lark import** (`pnpm nocobase app edu import-lark`, DS-60): `cli/commands/edu/import-lark.ts` → `server/edu/lark/`: `nguon.ts` reads the Base through `lark-cli` (a `LarkSource`; tests use `tests/helpers/lark-fixture.ts`), `ke-hoach.ts` builds the whole plan as a pure function, `ghi.ts` writes it in one transaction, `nhap.ts` runs and reports. Dry run is the default and writes nothing, not even the log (`eduNhapLarkNhatKy`). Unconfirmed rules live in one file, `chua-xac-nhan.ts` (the `Deal HP` ones are the `DEAL_RULES` switches). Parents come from `Contact` (`lark:contact:<rec>`) and packages from `Deal HP` (`lark:deal:<rec>`, `loai = mua`, price 0: `Deal HP` has no amount); a student with Deals has his balance recomputed as Σ packages − every deducted session of 2024–2026, one without keeps the opening package (`lark:sodu:<rec>`). Keys of earlier runs (`lark:ph:*`, `lark:sodu:*`) are recognised, never duplicated (`docs/lark/nhap-production.md`). **The money** is in `Tổng Deal (HP + book)` (DS-61): `thanh-toan.ts` turns its tuition into `eduThanhToan` rows (`externalId = lark:tongdeal:<rec>`, `hinhThuc = khong_ro`, branch of the student), written in the same transaction after the packages and so simulated by the dry run too; a row without a student, a date or a package is reported with its amount, never guessed. It is optional: an app that cannot see the table imports as before. Rules to confirm: `TONG_DEAL_RULES`. **Books** (`sach.ts`, DS-61 E): the table `Sách` becomes the catalogue `eduSach` (`lark:sach:<rec>`, optional table, written in the same transaction, never edited afterwards, a symbol typed by hand is kept). The catalogue is global (`allRecords`): only the administrator manages it; the grants were added to the seeded sets by `202611130003_edu_sach_grant`, which is why `scripts/generate-edu-permission-seed.mts` leaves `edu.sach` out of `…0002` (on Windows turn the seed's CRLF into LF before running the generator). **Books handed out** (`eduPhatSach`, DS-61 E2): one row per book given to a student; the page `edu.phatSach` and the composite `edu.phatSach` (view, manage) are held by the administrator (all), the branch manager (`edu.myBranches`, by the student of the row) and the accountant (view); a coach has neither (the row carries a price). It is written only by `POST /phatSach/ghi`, which takes the branch from the student and `tienSach = giaBan - uuDai` from the book at that moment (kept in the row, so a later price change rewrites nothing); the record API only reads it. Grants: `202611140002_edu_phat_sach_grant` (the generator leaves `edu.phatSach` out of `…0002` too). The database is the truth for what was imported: written packages and attendance are never edited, Lark differing only warns. `--dry-run` simulates the commit (`moPhongGhi`: the same write in a transaction, balances read, rolled back) and prints "số dư sau nhập" next to the Lark-only "tính lại"; never compute the after-import balance on paper again. `externalId` is never `''` (use `externalIdOrNull`). Output and log hold counts, Lark ids and codes, never a name, phone, email or date of birth. Run guide and rollback: `docs/lark/nhap-production.md`. The setting `EDU_TRU_BUOI_VANG_KHONG_PHEP` is fixed on a session at its first save (`eduBuoiHoc.truVangKhongPhep`), like `truVangCoPhep`.
- **Lists and detail pages** (DS-60): list pages read one page of 25 on the server (`usePagedRows` in `client/pages/edu/kit.ts`: `limit`, `offset`, a filter built with `buildFilter`, the total from `count`; search is a case-insensitive `includes` over the page's fields). `useRows` is only for lookups (names of classes and branches) and reads every page up to 2,000 rows. The student file (`/hoc-vien/:id`) and the class page (`/lop/:id`) are read-only and reuse the page grant of their list; they read through the record APIs, so scope and field policy decide what shows, and a record out of scope is "not found". A tab shows only if the person may `view` its composite (`edu.phuHuynh`, `edu.diemDanh`, `edu.goiHoc`, `edu.soDu`). Tests: `tests/client/edu-detail.test.tsx`, `tests/server/edu-detail-scope.test.ts`.

- **Session content and awareness score** (DS-61): the four text columns of `eduBuoiHoc` (`keHoachDay`, `kienThucMoi`, `giaoBtvn`, `keHoachBuoiSau`) and `eduDiemDanh.yThucDiem` (0–10) are written by the Lark import and are **not permission fields**, so no standard record API returns them. They are read and written only by `POST /buoiHoc/noiDung/xem` (`edu.diemDanh` `view`) and `/buoiHoc/noiDung/luu` (`edu.diemDanh` `record`) in `server/routes/edu-noi-dung-buoi.ts`, both behind the caller's `edu.buoiHoc` scope (out of scope is 404). A score is written only for a student who already has an attendance row in that session (404 `EDU_ATTENDANCE_NOT_FOUND`); a field not sent stays, an empty text clears it, and a save never touches the balance or the attendance status. Page: the "Nội dung buổi học" block and the awareness column of `client/pages/edu/diem-danh.tsx`. Tests: `tests/server/edu-noi-dung-buoi.test.ts`.
- **Negative-balance report** (DS-61): `baoCao` kind `soDuAm` (gate `edu.hocVien`) lists studying students whose `soBuoiConLai` is below zero, worst first, with `buoiNo`. It is the list to tell parents that the next term's fee is due (the 103 students that kept their old balance after DS-60 were decided to be handled this way, 13/11/2026).

## Which sessions were deducted from which package (DS-60 PR 3)

`POST /goiHoc/chiTiet` (`server/routes/edu-hoc-phi.ts`) answers `{ goiHocId }` with the package, `daDung`, `conLai`, the
sessions deducted from it (`cacBuoi`) and `vuotSoDu` (sessions beyond everything the student bought). It needs
`edu.goiHoc` `view` for the package (so a coach gets 403 and a branch manager sees their branch only) and `edu.soDu`
`view` for the ledger. Nothing is stored: `server/edu/phan-bo-goi.ts` works the allocation out on every read, first in
first out, from the packages (by `ngayMua`, then id) and the ledger (the sum per attendance row, so a refund cancels its
deduction; a positive `dieu_chinh` without a package counts as a package of its own, a negative one as a deduction
without a session). A deduction takes the earliest package with room, whatever the date of the session; the rules are
at the top of that file and are the only place to change them. `useRows(name, { newestFirst: true })` reads a growing
collection (sessions) newest first, so its cap of 2,000 rows never drops the newest.

## Editing and removing (DS-60 PR 4)

Edit buttons and dialogs live in `client/pages/edu/sua-xoa.tsx` (`RowManage` for branch, class, student and parent;
`NoteButton` for a coach's note; `UnlinkButton` for a student–parent link). They use the standard `updateOne` and
follow the person's `manage` grant, but the server decides: `server/routes/edu-data.ts` checks the grant, the record
scope and the allowed fields, and `server/edu/sua-ban-ghi.ts` (`checkUpdate`, pure, no database) checks the values (a
status from the list, a phone number already normalised, a class level key that agrees with its order). A class or a
timetable row cannot be moved to a parent outside the caller's scope. **Nothing is deleted except a parent that no
student link and no consent refer to** (`POST /phuHuynh/xoa`): a branch is set to `tam_dung`, a class to `da_dong`, a
student to `da_nghi`, so attendance, packages and the balance ledger stay. Never add a hard delete for those three. A
student's class changes only through `/hocVien/chuyenLop`; the balance and the level never through `updateOne`. Removing
a package is not offered; when it is, it must write a ledger row that returns its sessions (see `phan-bo-goi.ts`).
